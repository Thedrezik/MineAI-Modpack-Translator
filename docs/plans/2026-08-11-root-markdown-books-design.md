# Поддержка корневых Markdown-книг

## Проблема

Обработчики BETAv23 распознавали Markdown-книги только по каталогу
`/en_us/`. Из-за этого AE2 с исходниками в `ae2guide/` и Modern
Industrialization с исходниками в `mi_guidebook/` не попадали в анализ.
Простое удаление условия опасно: старый код использовал исходный путь как
целевой и мог записать перевод поверх английской страницы.

## Рассмотренные варианты

1. Добавить отдельные проверки по mod id AE2 и MI. Это быстро, но каждый новый
   мод потребует очередного исключения.
2. Принимать любой `.md` в JAR. Это создаёт ложные книги в каталогах текстур,
   документации и других ресурсов, а также не определяет безопасный путь записи.
3. Определять формат по структуре архива. Этот вариант выбран: он не зависит от
   mod id и использует уже существующие языковые каталоги как описание формата.

## Решение

`MarkdownBookLocator` ищет контейнер книги внутри `assets/<namespace>` по
характерным именам (`guide`, `manual`, `book`, `lexicon`, `codex`, `wiki`).
Стандартный путь `/en_us/` заменяется на целевой язык. Для английских страниц в
корне контейнера локаль вставляется сразу после контейнера. Если архив содержит
каталоги `_ja_jp`, `_pt_br` и аналогичные, сохраняется подчёркнутая схема и
создаётся `_ru_ru`; иначе используется `ru_ru`.

Один и тот же определитель применяется в анализаторе, оценщике количества строк
и обработчике JAR. Уже локализованные каталоги исключаются из английских
источников. Каталоги текстур, моделей, звуков, shaders, blockstates и lang не
могут становиться корнем книги.

## Проверка

- стандартный `manual/en_us/page.txt` сохраняет прежнее поведение;
- AE2 пишет только в `ae2guide/ru_ru/...`;
- MI пишет только в `mi_guidebook/_ru_ru/...`;
- исходный английский путь никогда не используется как целевой;
- анализатор и оценщик возвращают одинаковые результаты.
